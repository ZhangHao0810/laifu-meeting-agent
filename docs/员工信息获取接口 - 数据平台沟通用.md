## 一、系统基础接口（内网直连）

> **请求地址前提**：接口对应 `http://10.108.135.90:9092`，必须在公司内网网络环境下访问。
> **Content-Type**：`application/json`
> **请求方法**：POST

### 1. 查询部门信息（getDepartmentInfo）

**接口用途**  
根据部门 ID 或部门名称查询部门详细信息，包括部门基本信息、层级关系、部门内成员列表等。

> [!IMPORTANT]
> **最重要的数据字段**：
> - **ORG_ID** - 部门ID（唯一标识）
> - **ORG_NAME** - 部门名称
> - **ORG_PATH_NAME** - 部门完整路径
> - **PARENT_ORG_ID** - 父部门ID
> - **MEMBER_IDS** - 部门成员ID列表
> - **MEMBER_CODES** - 部门成员工号列表

#### 请求参数（Body）

| 字段   | 类型   | 必填 | 说明                     | 示例值    |
|--------|--------|------|--------------------------|-----------|
| orgId  | string | 否   | 部门ID（与orgName二选一） | "2013695808098356143" |
| orgName | string | 否  | 部门名称（与orgId二选一） | "AI平台与应用产品研发中心" |

> [!TIP]
> **参数说明**：`orgId` 和 `orgName` 至少传一个，优先使用 `orgId` 查询（更精确）。

**请求示例**

```json
{
  "orgId": "2013695808098356143"
}
```
或
```json
{
  "orgName": "AI平台与应用产品研发中心"
}
```

- `ORG_LEVEL` → 可用于判断部门层级深度

### 2. 根据姓名查询员工信息（getUserByName）

**接口用途**  
根据员工姓名查询员工的基本信息（主要用于获取工号、BASE地等参数）。

#### 请求参数

| 参数名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| name | string | 是 | 员工姓名（精确匹配） |

**请求示例**
```json
{
  "name": "王星"
}
```

#### 返回参数

| 参数名 | 类型 | 说明 |
|--------|------|------|
| content | array | 员工信息列表（可能有重名） |
| content[].CODE | string | 员工工号 |
| content[].NAME | string | 员工姓名 |
| content[].ORG_PATH_NAME | string | 所属部门完整路径 |
| content[].BASE_NAME | string | BASE 地 |
| content[].PHONE | string | 联系电话 |
| content[].EMAIL | string | 邮箱地址 |
| message | string | 返回消息 |
| records | integer | 返回记录数 |
| successFlag | boolean | 是否成功 |

**返回示例（正常）**
```json
{
  "content": [
    {
      "CODE": "11528",
      "NAME": "王星",
      "PINYIN": "wang星",
      "SEX_NAME": "男",
      "EMAIL": "wang星@zhongfu.net",
      "PHONE": "18942667857",
      "ORG_PATH_NAME": "公司\\某科技有限公司\\业务中台\\AI产品研发中心",
      "BASE_NAME": "深圳市",
      "IM_OPEN_ID": "c9f2a2c0ca2883f4ada5f11c"
    }
  ],
  "message": "Api access succeeded",
  "records": 1,
  "successFlag": true
}
```

**特殊情况：未找到员工**
```json
{
  "content": [],
  "message": "Employee not found",
  "records": 0,
  "successFlag": true
}
```

**特殊情况：存在重名员工**
```json
{
  "content": [
    {
      "CODE": "10001",
      "NAME": "张伟",
      "ORG_PATH_NAME": "公司\\某科技有限公司\\业务前台",

    {
      "CODE": "10523",

      "ORG_PATH_NAME": "公司\\某科技有限公司\\业务中台\\AI产品研发中心",

    }
  ],

  "records": 2,
```

### 3. 批量查询员工信息（getBatchUserInfo）

**接口用途**  
根据一批员工的工号，批量查询员工详细信息。

#### 请求参数

| 参数名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| codes | array | 是 | 员工工号列表 |
| fields | array | 否 | 需要返回的字段列表，不传则返回全部字段 |

**请求示例（查询全部字段）**
```json
{
  "codes": ["11528", "11529", "11530"]
}
```

**请求示例（只查询指定字段）**
```json
{
  "codes": ["11528", "11529", "11530"],
  "fields": ["CODE", "NAME", "BASE_NAME", "PHONE", "ORG_PATH_NAME"]
}
```

#### 返回参数

| 参数名 | 类型 | 说明 |
|--------|------|------|
| content | array | 员工信息列表 |
| content[].CODE | string | 员工工号 |
| content[].NAME | string | 员工姓名 |
| content[].BASE_NAME | string | BASE 地 |
| content[].PHONE | string | 联系电话 |
| content[].ORG_PATH_NAME | string | 所属部门 |
| content[].* | any | 其他字段（根据 fields 参数决定返回） |
| notFound | array | 未找到的工号列表 |
| message | string | 返回消息 |
| records | integer | 成功查询的记录数 |
| successFlag | boolean | 是否成功 |

### 4. 模糊搜索员工（searchUsersByName）

**注意**：此接口为可选扩展。

**接口用途**  
根据姓名关键词进行员工的快速模糊搜索。

#### 请求参数

| 参数名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| keyword | string | 是 | 搜索关键词（支持匹配姓名或拼音） |
| limit | integer | 否 | 返回结果数量限制，默认 10，最大 50 |

**请求示例**
```json
{
  "keyword": "王",
  "limit": 5
}
```

#### 返回参数

| 参数名 | 类型 | 说明 |
|--------|------|------|
| content | array | 匹配到的员工列表 |
| content[].CODE | string | 员工工号 |
| content[].NAME | string | 员工姓名 |
| content[].PINYIN | string | 姓名拼音 |

| records | integer | 返回当前查询下发的数据量 |
| totalMatches | integer | 总匹配的数据量（可能大于本次返回数） |

## 三、使用场景及说明

### 1. 常见使用场景示例

**场景 A: 根据多位人员姓名列表查询 BASE 地分布**
通过串联方法实现高效率查询：
1. 遍历名单，使用 `getUserByName` 获取每一个有效人员的真实工号。
2. 使用收集到的工号数组调用 `getBatchUserInfo` 拿到人员全量详情对象。

```javascript
// 第一步：根据姓名获取工号
const names = ['王星', '郑纯桂英', '郭露亮'];
const codes = [];

for (const name of names) {
  const result = await getUserByName({ name });
  if (result.records > 0) {
    codes.push(result.content[0].CODE);
  }
}

// 第二步：批量查询详细信息
const userInfo = await getBatchUserInfo({
  codes: codes,
  fields: ['CODE', 'NAME', 'BASE_NAME', 'PHONE']
});

console.log(userInfo.content);
```

**场景 B: 查询目标部门所有成员的办公点（BASE 地）分布**
1. 先利用 `getDepartmentInfo` 拿到部门成员的人员工号全集 `MEMBER_CODES`。
2. 数据透传到 `getBatchUserInfo` 并声明提取所需字段。
3. 本地聚类统计各省市比例数据。

```javascript
// 第一步：获取部门信息
const dept = await getDepartmentInfo({ orgName: 'AI产品研发中心' });
const codes = dept.content[0].MEMBER_CODES;

// 第二步：批量查询成员信息
const members = await getBatchUserInfo({
  codes: codes,
  fields: ['CODE', 'NAME', 'BASE_NAME']
});

// 第三步：统计 BASE 地分布
const baseDistribution = {};
members.content.forEach(member => {
  const base = member.BASE_NAME;
  baseDistribution[base] = (baseDistribution[base] || 0) + 1;
});

console.log(baseDistribution);
// 结果: { '深圳市': 45, '北京市': 32, '上海市': 28, ... }
```

### 2. 接口能力对比

| 接口 | 查询方式 | 返回数据量 | 适用场景 |
|------|----------|-----------|----------|
| `getCloudUserInfo` | 单个工号 | 单个员工全部字段 | 原生获取。已知工号，查询特定人员详细信息 |
| `getUserByName` | 单个姓名 | 单个/多个员工基本信息 | 已知人员真实姓名以获取工号；遇到重名辅助查错 |
| `getBatchUserInfo` | 多个工号 | 多个员工指定字段 | 大批量分析。例如整个组织全员的人口属性聚类、状态巡检 |
| `searchUsersByName` | 关键词模糊搜索 | 多个员工基本信息 | 不确定完整姓名时进行模糊智能检索 |

### 3. 性能及限制

- **getUserByName**: 单次查询耗时通常 `< 50ms`。
- **getBatchUserInfo**: 
  - 建议单次批处理限制提交工号量为 **不超过 100 个**。
  - 每额外增加 10 个工号，响应计算时长预估会提升 5-10ms 左右。
  - 单次提交 100 个工号时，请求响应耗时预期约在 `100-150ms` 之间。

### 4. 错误码说明

| 错误状态 | 业务定义说明 |
|--------|------|
| **400** | 请求参数错误（缺少必填参数或参数格式不合法） |
| **404** | 未找到任何能匹配查询入参的部门/人员数据 |
| **500** | 服务端内部异常。需联系数据基座侧研发协查 |

### 5. 建议实现优先级与备注

**在系统侧优先推荐的开发与落地方案：**
1. 🟢 **高优先级**: `getBatchUserInfo` - 由于支持指定返回字段进行批量瘦身，在日常调用场景是最为省时提效的方法模块。
2. 🟡 **中优先级**: `getUserByName` - 完成由模糊名称转变为唯一工号标识的前置必需操作。
3. ⚪ **低优先级**: `searchUsersByName` - 作为增加用户体验的一项可选输入建议。

> [!NOTE]
> **开发规约备忘录：**
> - **扩展接口与基座关联**：所有扩展接口的返回包装响应体定义，必须绝对对齐现有的 `getCloudUserInfo` 的范式，保障历史调用的平滑。
> - **降量设计**：为减少服务器 I/O 与带宽负荷，对于能拿到集合的对象均支持传递 `fields` 来做列数据修剪。
> - **查询缺口处理**：批量接口执行完会携带一个数组 `notFound`，业务消费侧应当在返回报文中检查此数组判断是否有遗落数据并加以提示。
